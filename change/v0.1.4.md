## [0.1.4]

Date of Release: 2025-03-01

Programming Language: Python 3.12+

Author: Ichiru Pham

This is the large release but under the "patched" version. A lot of thing news, including the re-calibration of all parameters, the new algorithm for WAL management and anti-wraparound tuning. The default parameters (without correction tuning) are now more suitable across workload type, even for the small system. 

### Highlights

- Major re-calibration of all parameters and introduction of a new algorithm for WAL management and anti-wraparound tuning, improving reliability and performance across workloads.
- Significant changes to WAL parameters: reduced wal_segment_size upper bound (2 GiB → 128 MiB), new logic for min_wal_size, max_wal_size, and wal_keep_size based on WAL volume capacity.
- Default parameters are now more suitable for a wider range of systems, including small servers.
- Introduction of the `database_size_in_gib` parameter for better anti-wraparound tuning estimation, defaulting to 10 GiB and capping at 32 TiB.
- Improved autovacuum and checkpoint algorithms, including new defaults and scaling based on system size and workload.
- Enhanced documentation for both backend and UI, making formulas and logic more transparent for users and developers.

* The upper bound of `wal_segment_size` is reduced from 2 GiB to 128 MiB. The reason of change is added directly from the code: "Increase this value is only beneficial when" 
  * (1) you have a lot of incoming WRITE beyond 16 MiB per transaction 
  * (2) high WAL file rotation time during workload (usually at old kernel and old PostgreSQL version) 
  * (3) high archive transfer due to small files (a lot of 16 MiB files) that translated into a mix of random and sequential IOPS, and 
  * (4) low number of allowed files in filesystem.

* Introduce the parameter `database_size_in_gib` in the basic configuration (default to 10 GiB and maximum at 32 TiB). This is used in the anti-wraparound tuning to be served as the minimum boundary hopefully the data volume can scan randomly at 30% WRITE IOPS on the full data files (not index files). If user don't know the amount of data they would have (for example new on-boarded application), then set to zero value meant a 60% of used volume in the data partition.
